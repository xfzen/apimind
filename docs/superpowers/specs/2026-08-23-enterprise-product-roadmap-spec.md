# ApiMind 企业产品 Roadmap Spec

**状态：** 已确认

**日期：** 2026-08-23

**范围：** 产品方向、阶段优先级与产品门槛；不包含实施排期和任务拆分

**G0 架构依据：** [ECP Requirements & Technical Design](2026-08-23-enterprise-control-plane-spec.md)；[ApiMind Enterprise Connector Profile](2026-08-23-apimind-enterprise-connector-profile-spec.md)

## 1. 决策摘要

ApiMind 下一阶段不以继续完善普通 API 文档功能为主，也不以完整追赶竞品功能数量为目标。产品主线调整为：

> 先补齐企业和中小团队采用 ApiMind 的必要条件，使其从“功能可用的自托管 API 工具”成为“企业敢于接入真实团队、真实凭据和真实 API 资产的平台”。

企业软件不是按功能总分做加法判断。身份、权限、审计、凭据安全、数据主权和恢复能力属于企业准入门槛；其中任何一项缺失，都可能让采购或生产部署直接不通过。跨 YApi、Postman、Insomnia、Bruno、Hoppscotch 的长期用户反馈进一步说明，企业通过准入后，还必须解决迁移同步、环境鉴权、Schema 精度和持续执行，产品才能真正替换现有工具并长期使用。

因此 Roadmap 使用以下顺序：

1. **G0 企业准入门槛：** 私有部署和数据控制、身份与用户生命周期、RBAC、审计、Secret、服务账号、备份恢复和安全升级；
2. **G1 企业替换门槛：** Contract Source & Sync、Schema 精度、Environment/Auth/Network、历史恢复和企业规模性能；
3. **E1 持续工程能力：** Runner、定时同步与测试、通知、Contract Validation 和安全 Mock；
4. **E2 团队治理能力：** 变更审核、发布和标准化规则；
5. **D1 ApiMind 差异化能力：** 受治理的 Agent/MCP、Proxy/Trace、Scenario、E2E 与回放；
6. **P1 平台扩展能力：** 多协议、存储和部署架构扩展。

G0 是全局第一目标。G0 基础配置未通过前，不以 G1 或差异化功能作为主投入。若目标企业明确要求 SAML、SCIM、SIEM、HA 或外部 Vault/KMS，这些能力对该客户即升级为 G0 条件性门槛，而不是因为通常位于后续阶段就延后。

这不是从 85 分继续优化到 95 分，而是补齐企业采用模型中的关键零分项。

## 2. 第一性原理

### 2.1 企业首先购买的是可控性，其次才是效率

企业将 API 平台接入真实研发流程时，首先需要回答六个准入问题：

1. 系统能否完全运行在企业控制的网络和基础设施中；
2. 谁可以登录，离职或调岗后能否立即失去访问权；
3. 谁可以查看、修改、发布或导出哪些 API 资产；
4. 人、CI 和 Agent 是否使用独立、最小权限、可撤销的身份与凭据；
5. 安全人员能否追溯身份、权限、配置、凭据和关键数据操作；
6. 故障、升级失败或误操作后，数据能否可靠恢复。

通过准入后，还需要回答三个替换与持续使用问题：

1. 现有 YApi、OpenAPI 或代码生成契约能否完整迁移并持续同步；
2. 请求与响应 Schema、引用、枚举、状态码和必填信息是否准确；
3. 多环境、鉴权、Token、Secret、代理和证书能否安全复用。

完成替换门槛后，再回答持续工程问题：GUI 中的核心能力能否由 G0 机器身份在 Runner 或定时任务中稳定重复执行。

如果这些问题没有产品化答案，现有文档、Mock、测试集合和 MCP 即使可以使用，也难以成为企业的长期 API 基础设施。

### 2.2 企业价值是乘法模型

本 Roadmap 使用以下判断模型，而不是按功能数量排序：

```text
企业生产可采用性 = 核心业务可用性
                 × G0 企业准入门槛通过度
                 × G1 企业替换门槛通过度
                 × 组织流程适配度
```

任一项接近零，整体企业可采用性都会显著下降。当前核心编辑业务已经可用，因此首先必须消除 G0 中会直接否决企业采购和生产部署的零分项；G0 通过后，再解决 G1 中决定产品能否替换现有工具并持续使用的问题。

### 2.3 二八原则

竞品提供的企业功能很多，但二八原则要求先区分两类门槛。

**G0 企业准入门槛：**

- 私有部署、离线运行、数据控制和可关闭的外部依赖；
- 身份接入、成员生命周期、会话撤销和分层权限；
- 服务账号、Token 生命周期、Secret 安全和公开分享控制；
- 全局审计、完整导出、备份恢复和升级回滚；
- 目标企业明确要求的 SAML、SCIM、SIEM、HA 或外部 Vault/KMS。

**G1 企业替换门槛：**

- 导入、持续同步、冲突预览和智能合并；
- Environment、Auth Profile 和 Network Profile；
- Schema 准确性、公共模型和导入损失诊断；
- 资源历史、Diff、单资源恢复和大项目性能。

Roadmap 先完成 G0，再完成 G1；不在门槛完成前复制计费、门户、复杂审批、多协议和全部高级测试能力。

### 2.4 证据分级

产品优先级不再由单一 issue 频率决定：

| 证据类型 | 用途 | 优先级影响 |
| --- | --- | --- |
| 企业采购、合规、安全问卷和生产试点阻塞 | 判断是否属于准入门槛 | 可进入 G0 |
| 竞品企业版共同能力 | 判断市场是否已形成稳定预期 | 支持 G0 或 G1，但仍需目标客户验证 |
| 开源 issue 和社区高频反馈 | 判断日常摩擦与替换意愿 | 主要进入 G1 或 E1 |
| ApiMind 架构与差异化机会 | 判断长期竞争优势 | 进入 D1 或 P1 |

同一能力可以因目标客户不同改变阶段。例如 SAML 对一般中小团队是后续能力，但对将 SAML 写入采购清单的企业就是 G0 条件性门槛。

## 3. 目标客户与核心角色

### 3.1 主要客户

**企业研发组织**是商业能力的主要目标：需要私有部署、统一身份、安全审计、组织权限和生产运维保障。

**中小研发团队**是产品采用和口碑扩散的主要目标：需要低成本部署、清晰成员权限、可靠备份、变更记录和团队通知，但通常不需要复杂组织架构。

两类客户共享同一套核心产品，不维护两套架构。企业能力应按需启用，不能让中小团队的首次使用变复杂。

### 3.2 核心角色

| 角色 | 核心诉求 |
| --- | --- |
| 实例管理员 | 安装、升级、备份、恢复、身份源、安全策略和全局审计 |
| 工作区管理员 | 成员、角色、项目范围、共享策略和操作追溯 |
| API 维护者 | 创建和修改接口、管理 Mock/测试、处理变更和发布 |
| API 使用者 | 查阅、搜索、调试和订阅变更，不应获得修改权限 |
| 自动化身份 | CI、服务集成和 AI Agent 使用独立身份、有限权限与可撤销凭据 |
| 安全审计者 | 只读查询和导出审计记录，不参与日常 API 编辑 |

## 4. 产品定位

ApiMind 的短期竞争定位是：

> 面向企业和中小研发团队的自托管 API 协作平台，兼容 YApi 主要使用习惯，同时提供现代化、安全可治理的团队能力与 Agent/MCP 接入。

其中：

- **YApi 兼容**降低已有团队的迁移成本；
- **自托管**满足数据主权和内网使用；
- **企业治理**决定能否进入真实生产环境；
- **Agent/MCP**形成后续差异化，但必须继承相同权限和审计边界。

ApiMind 不以短期覆盖 Apifox、Postman 或 SwaggerHub 的全部能力为目标，也不以成为通用 API 网关或测试平台为第一阶段目标。

### 4.1 内置能力与扩展边界

高频、标准、跨企业重复出现的能力由官方产品体系提供。其中身份、会话、企业授权、服务身份和统一审计由 Enterprise Control Plane（ECP）提供，ApiMind 只实现产品 `ecp-connector`；Casdoor 直接承担 IAM 和优先采用的 Casbin 授权引擎：

- Enterprise Identity：通过 Casdoor 提供本地账号、LDAP、OIDC、SAML 及 MFA；
- User Administration：通过 `ecp-ui` 提供用户、禁用、产品会话和角色管理；
- Contract Source & Sync：来源绑定、比较、合并、报告和定时同步；
- Auth Profile 与 Secret Reference：标准鉴权和凭据安全；
- Notification Channel：Webhook 与常用企业消息渠道；
- Runner / Scheduled Job：无人值守同步、验证和测试；
- Standard Export：完整、可恢复、可迁移的数据导出；
- Safe Mock Runtime：隔离、限权、可审计的动态行为。

客户私有、行业专属或无法标准化的逻辑保留在受控 Adapter/Handler 边界：

- 企业专用 SSO 或身份映射；
- 医疗、工业等行业状态校验；
- 厂商私有协议和特殊签名算法；
- 客户专属通知负载和业务处理器。

扩展边界必须继承权限、Secret、资源限制和审计规则，不能重新引入任意宿主代码执行。

## 5. 竞品基线结论

本 Spec 同时参考竞品已经产品化的能力和开源项目长期 issue。issue 信号用于判断用户反复遇到的问题，竞品文档用于判断这些问题是否已经形成稳定产品能力。这里是定性强度判断，不宣称不同社区之间存在统一口径的数量统计。

| 竞品信号 | 证据类型 | 体现的企业需求 | ApiMind Roadmap 结论 |
| --- | --- | --- | --- |
| Apifox 提供私有部署、企业管理后台、SAML/OIDC/LDAP、项目权限、自定义角色、通知和版本历史 | 竞品企业版共同能力 | 国内企业重视内网部署、身份接入、权限和协作治理 | 私有部署、基础身份、权限、审计和运维进入 G0；特定协议按客户采购清单条件性进入 G0 |
| Postman Enterprise 提供 SSO、SCIM、RBAC、审计日志、服务账号和 API Governance | 竞品企业版共同能力 | 大型组织需要统一人员生命周期、非人身份和治理策略 | 服务账号与凭据生命周期进入 G0，不能随 Runner 一起后置 |
| SwaggerHub 提供组织、团队、成员自动管理及资源级角色 | 竞品企业版共同能力 | 权限必须落到具体 API 资源范围，而不是只有系统管理员和普通用户 | 在既有 workspace/project 层级上先建立可解释权限模型；更复杂组织模型需要验证 |
| YApi、Postman 和 Bruno 用户反复要求从 OpenAPI/Swagger 来源持续刷新，同时保留人工补充、鉴权、脚本和环境 | 社区高频反馈 | “导入一次”不能解决长期契约漂移，静默覆盖会破坏用户信任 | Contract Source & Sync 进入 G1，并提供 dry-run、合并策略和 drift report |
| Insomnia、Postman 和 Bruno 用户反复要求本地文件、离线运行、Git/CI 和可恢复数据 | 企业限制与社区高频反馈 | 自托管关联数据所有权，文件和 CI 关联可迁移性与自动化 | 无云依赖、完整导出和恢复进入 G0；文件/CI 工作流进入 G1/E1 |
| YApi、Bruno 和 Hoppscotch 用户长期反馈 OAuth、Token、代理、自签名证书和通用 OIDC 问题 | 社区高频反馈 | 请求能否在企业真实网络和鉴权环境运行，是日常高频门槛 | Environment/Auth/Network 进入 G1；OIDC 身份接入属于 G0 |
| Apifox 已将 Schema、公共模型、导入、Mock、验证和测试串联 | 竞品产品化能力 | Schema 精度是文档、Mock、测试和代码生成的共同基础 | Schema fidelity 和导入损失诊断进入 G1，并先于高级测试与多协议 |

## 6. 当前基础与主要缺口

### 6.1 已有基础

ApiMind 当前已经具备：

- 自托管的 Go Server、Web 和 MongoDB 运行形态；
- workspace / project / cat / interface 核心层级；
- YApi 兼容的成员管理和基础角色；
- 接口文档、Mock、测试集合、导入导出和文档工作台；
- MCP 契约查询及受确认约束的写入；
- 基础 Log 数据结构及部分契约写入审计；
- 构建、安全和兼容性验证基础。

### 6.2 需要优先补齐的缺口

| 门槛 | 能力域 | 当前判断 | 产品缺口 |
| --- | --- | --- | --- |
| G0 | 身份 | 本地账号可用；LDAP 入口存在但真实绑定未完成 | 缺少完整企业 SSO、目录接入、人员停用和会话撤销机制 |
| G0 | 权限 | workspace/project 成员和 `owner/dev/guest` 基础角色可用 | 缺少实例级管理、资源级读写边界、审计者和自动化身份角色 |
| G0 | 审计 | 已有 Log 和部分契约写入记录 | 缺少覆盖身份、成员、权限、配置、Token、导出和关键数据操作的统一审计中心 |
| G0 | 凭据 | MCP Bearer Token 已有认证基础 | 缺少服务账号、权限范围、到期、轮换、撤销和管理界面 |
| G0 | 运维 | 本地 Compose 和生产形态启动可用 | 缺少产品化离线交付、备份恢复、升级回滚、兼容检查和运维可观测性 |
| G0 | 数据暴露 | 已有 workspace/project 可见性和文档访问基础 | 缺少实例级公开分享策略、外部访问控制和敏感导出治理 |
| G1 | 导入与同步 | 已有 YApi JSON、Postman、HAR、Swagger 导入和批量写入基础 | 缺少持久 Source Binding、dry-run、冲突预览、字段级合并、漂移报告、失效资源策略和幂等重试 |
| G1 | Schema | 接口请求/响应结构和 Schema 编辑基础可用 | 缺少公共 Components、`$ref`、多状态码一致处理、Example 分离、字段损失诊断和 Contract Validation |
| G1 | 环境与鉴权 | 项目环境和请求调试基础可用 | 缺少正式 Auth Profile、OAuth2 生命周期、Secret Reference、变量作用域和跨执行端一致语义 |
| G1 | 企业网络 | 本地代理和同源 Web 运行边界可用 | 缺少请求执行所需的 HTTP Proxy、自签名 CA、Client Certificate、超时和网络策略模型 |
| G1 | 变更恢复 | 接口日志及部分前后状态已经存在 | 缺少统一 Diff、单资源恢复和项目完整迁移包 |
| G1 | 大项目与迁移 | 当前核心流已通过基础 Smoke | 大数据量分页、延迟加载、导入异步化、迁移可恢复和升级性能仍需要验证 |
| E1 | 集成 | MCP 和基本导入导出可用 | 缺少通用 Webhook、企业消息平台和稳定 CI/Runner 路径 |

标记为当前判断的内容在进入实施 Spec 前仍需通过代码、契约和真实部署逐项验证；不以历史文档或旧 YApi 页面存在作为已实现证据。

## 7. Roadmap

Roadmap 不承诺日期。每一门槛和阶段以前一项的产品验收结果为进入条件，不以完成若干页面或接口作为结束标准。

### G0：企业准入门槛

**目标：** 先消除会直接否决企业采购、安全评审和生产部署的零分项。G0 是全局第一目标，不与后续功能主线并行争夺优先级。

#### G0.1 私有部署、数据控制与恢复

- 提供版本化、可复现、无 ApiMind 官方云依赖的正式发行组合；
- 支持无外网运行，Telemetry 必须透明且可关闭，外部字体、CDN、认证和 AI 服务必须可替换或关闭；
- 提供配置校验、健康检查、结构化日志和基础运行指标；
- 提供产品化备份、校验、恢复演练和恢复结果确认，不要求用户直接访问数据库；
- 提供实例级完整数据导出和可迁移格式说明，企业数据不能只能依赖当前实例读取；
- 每次升级声明兼容范围、迁移步骤、失败回滚路径和不可逆变化，高风险迁移前自动生成可恢复快照；
- 商业部署提供可离线验证、状态透明的授权机制，授权异常不能损坏或锁死已有数据；
- TLS、域名、反向代理和持久化卷具有受支持配置和安全默认值。

#### G0.2 企业身份与用户生命周期

- G0 参考部署直接使用 Casdoor 管理 Organization、User、本地账号、MFA、上游 IdP 和 SSO，不在 ApiMind 内重复实现认证系统；
- 企业 LDAP/LDAPS、OIDC、SAML 等身份源统一接入 Casdoor，ApiMind 和后续产品通过标准 OIDC/OAuth 与受控 Casdoor Adapter 使用；
- 外部身份以 Casdoor 稳定用户标识映射到 ECP 的内部 Principal，再显式映射旧 YApi 用户；邮箱、用户名和 DN 不作为授权主键；
- ECP 建立可列出、可撤销的产品会话；身份停用后产品会话和个人长期凭据进入立即撤销流程；
- 默认采用预创建或邀请模式，未知身份拒绝；JIT 必须显式启用且不能自动授予业务资源权限；
- 企业身份、`ecp-ui` 和 `ecp-api` 由多个产品共享，ApiMind 不单独开发一套企业后台；
- SCIM、Trusted Header/Auth Proxy、复杂 Group Sync 等按目标企业要求条件性进入 G0。

#### G0.3 RBAC 与数据暴露控制

- 保持 `workspace / project / cat / interface` 为业务资源层级，不默认新增组织业务层级；是否需要跨 workspace 组织管理标记为“需要验证”；
- 增加实例管理员边界，实例管理员不自动获得所有业务数据的编辑权限；
- workspace 提供内置 `owner/admin/member/guest`，project 提供内置 `admin/editor/viewer`；
- 权限计算统一供 Web、HTTP API、MCP 和后续 Runner/CLI 使用；
- 项目和文档默认私有，实例和 workspace 管理员可以禁止公开分享、外部访问和敏感导出；
- 所有拒绝操作返回可理解、可审计的原因；基础配置使用内置角色，自定义角色按目标企业要求条件性进入 G0。

#### G0.4 审计、Secret 与机器身份

- 建立统一审计事件模型，覆盖登录、身份配置、成员、角色、项目、接口、文档、导入导出、Token、服务账号和高风险配置；
- 审计记录包含操作者、来源、目标、动作、结果、时间和必要的前后状态；
- 提供按操作者、资源、动作和时间查询及受权限保护的导出，普通业务管理员不能修改或删除审计记录；
- 引入服务账号，CI、集成和 Agent 不得绑定个人长期身份；
- Token 支持项目作用域、到期、轮换、禁用和撤销，原始 Token 只展示一次，持久化只保存不可逆摘要；
- 建立 Secret Reference 和集中脱敏基础，密码、Token、Cookie 和证书私钥不得出现在 Web、日志、报告、导出和错误信息中；
- 若目标企业要求 SIEM/Audit Sink 或外部 Vault/KMS，该能力条件性进入 G0。

#### G0.5 企业配置矩阵

G0 不等于为所有企业一次性实现全部高级能力。每个目标企业在试点前形成准入配置矩阵：

| 配置 | 基础企业配置 | 条件性企业配置 |
| --- | --- | --- |
| 身份 | Casdoor、本地账号、OIDC/LDAP/LDAPS、产品会话 | SCIM、Trusted Header、复杂 Group Sync；目标客户要求时补充其他协议 |
| 权限 | 固定 workspace/project 角色 | 自定义角色、跨 workspace 组织治理 |
| 审计 | 本地查询和导出 | SIEM/Audit Sink、定制保留策略 |
| 凭据 | 产品内 Secret、服务账号和 Project Token | 外部 Vault/KMS、企业 CA 或硬件密钥 |
| 部署 | 单实例自托管、备份恢复和安全升级 | HA、灾备、多节点或隔离区部署 |

基础企业配置是产品默认 G0。条件性配置只要出现在已承诺目标企业的采购、安全或生产清单中，就必须在该企业进入生产前完成，不能固定推迟到 P1。

#### G0 验收门槛

只有同时满足以下场景，G0 基础配置才算完成：

1. 实例管理员可以在隔离环境完成安装、配置校验和版本确认，核心功能不依赖外部云；
2. 运维人员可以完成完整数据导出、备份、恢复、升级失败回滚和恢复后数据校验；
3. 企业可以通过 Casdoor 接入真实 LDAP/LDAPS 或 OIDC，并验证创建、登录、内部 Principal 映射、停用和产品会话撤销；
4. workspace/project 权限在 Web、HTTP 和 MCP 中一致，公开分享和敏感导出可以被实例策略关闭；
5. 服务账号可以使用有限 Project Token 执行授权操作，轮换或撤销后旧凭据立即失效；
6. 身份、权限、凭据和关键数据写入可以查询和导出审计，普通管理员不能篡改记录；
7. Secret 和原始 Token 不会出现在页面、日志、报告、导出或错误响应中；
8. 中小团队可以使用 Casdoor 本地账号和最小 ECP 组合完成现有核心业务流，不要求额外部署企业 IdP；
9. 已承诺目标企业的条件性配置全部满足其采购、安全和生产清单。

### G1：企业替换与持续使用门槛

**目标：** G0 通过后，让 ApiMind 能够可靠迁移现有数据、适配真实企业 API 环境并长期替换现有工具。

#### G1.1 Contract Source & Sync

- 将 YApi、OpenAPI/Swagger 文件和 URL、Springdoc 等 OpenAPI 来源建模为持久化 Contract Source；
- 以 `method + normalized path` 作为接口稳定匹配基础，并为重命名、移动和来源变化保留可追踪关系；
- 同步流程固定为 `Source Binding → Compare → Preview → Merge → Report → Repeat`；
- 支持 dry-run，正式写入前展示新增、更新、冲突、失效和字段损失；
- 提供明确字段所有权和合并策略，默认保留人工说明、示例、Mock、测试和其他本地补充；
- 删除或失效接口不得静默清理，必须通过显式策略和预览确认；
- 批量写入必须幂等、可重试，并在部分失败后从安全位置继续；
- 同步报告同时提供人类可读和机器可读格式；
- YApi 迁移与日常 OpenAPI 同步使用同一匹配、合并和报告基础。

#### G1.2 Schema Fidelity

- 请求和响应使用严格结构化 Schema，不以描述文本代替结构；
- 支持公共 Components、`$ref`、枚举、required、多状态码响应和常见组合结构；
- Schema 与 Example 分离；
- 导入和导出报告无法表达、被降级或丢失的字段；
- 往返同步不能静默改变字段类型、必填状态、引用关系和状态码；
- 同一 Schema 基础供文档、Mock、响应验证、测试、代码生成和 Agent 使用。

#### G1.3 Environment、Auth、Secret 与 Network

```text
Environment      管 Base URL 与普通变量
Auth Profile     管 Basic、Bearer、API Key、OAuth2 与签名配置
Secret Reference 使用 G0 的安全存储与脱敏基础
Network Profile  管 HTTP Proxy、CA、Client Certificate、超时与网络策略
```

- 环境、鉴权和网络定义可在项目范围复用，并允许个人本地值覆盖团队非敏感默认值；
- OAuth2 覆盖常用授权模式、Token 获取、刷新、过期和自定义 Header；
- Secret 只通过引用进入请求执行；
- HTTP Proxy、自签名 CA 和 Client Certificate 在 Web 调试、Runner 和自动化中使用相同语义；
- 浏览器继续通过 Go 侧服务执行企业网络请求，不引入远端直连旁路。

#### G1.4 历史、恢复与企业规模

- 接口、文档、分组、环境和关键项目配置保留修改历史、来源及必要的前后状态；
- 提供结构化 Diff、单资源恢复和项目完整迁移包；
- 大项目使用分页、延迟加载和必要索引；导入与迁移任务不得阻塞主要交互；
- 长任务提供进度、重试、取消和恢复，不允许静默覆盖或静默丢失。

#### G1 验收门槛

1. 一个已有 YApi 或 OpenAPI 项目可以完成首次迁移，再次同步时预览差异并保留人工内容；
2. 同一来源重复同步结果幂等，冲突、字段损失、失效接口和部分失败都有明确报告；
3. 代表性复杂 Schema 可以导入、展示、导出并通过往返一致性验证；
4. 使用 OAuth2、Secret、企业代理和自签名 CA 的真实内网接口可以安全调试；
5. 用户可以查看 Diff、恢复单个资源并导出完整项目；
6. 达到目标企业规模的代表性项目可以完成加载、迁移和同步性能验证，具体规模在实施 Spec 中由真实样本确定。

### 阶段 E1：自动化执行基础

**目标：** GUI 中的核心能力可以由受限机器身份稳定、无人值守地执行。

#### E1.1 Runner 与定时任务

- Runner 使用 G0 已建立的服务账号和 Project Token，不新增独立认证旁路；
- Runner 可以部署在企业内网，复用 G1 的 Contract Sync、Environment、Auth、Secret 和 Network 模型；
- 支持定时 Contract Sync、定时接口测试、重试、超时和并发限制；
- 所有执行记录身份、来源、输入版本、结果和必要的脱敏日志；
- 输出适合 CI 判断的状态码和机器可读报告。

#### E1.2 Contract Validation 与安全 Mock

- 在统一 Schema 上提供请求/响应验证、字段丢失检查和最小规则集；
- Mock 支持确定性匹配、状态码、延迟、错误和受控场景；
- 动态代码不在主服务进程内执行，并限制 CPU、内存、时长和网络访问；
- Mock 按项目启用，执行结果和异常进入日志；
- 客户私有逻辑通过受控 Adapter 或 External Handler 边界接入，不允许任意宿主代码注入。

#### E1.3 通知

- 先建立统一 Webhook 事件模型，再提供邮件、飞书、钉钉和企业微信预设；
- 通知支持按 workspace、project、事件类型和严重程度订阅；
- 同步冲突、测试失败、Token 到期、备份失败和高风险权限变更可以触发通知；
- 通知负载默认脱敏并受访问范围约束。

#### E1 阶段验收门槛

1. 内网 Runner 可以使用服务账号完成定时同步和测试，不依赖个人登录态；
2. Web、MCP、CI 和 Runner 使用同一合并、Schema、Environment、身份和权限语义；
3. 同步漂移、验证失败和执行结果可以生成机器可读报告并触发 Webhook；
4. 动态 Mock 无法访问未授权宿主资源，并具有资源限制和执行日志；
5. G0 Token 轮换或撤销后，旧凭据不能启动新任务或继续取得新的执行权限。

### 阶段 E2：团队治理与发布协作

**目标：** 在数据同步和自动化基础可靠后，为有需要的团队提供受控 API 变更流程。

- 接口、文档、分组和关键项目配置形成一致历史视图；
- 对关键项目提供可选的草稿、待审核和已发布状态；
- 作者和审核者权限可以分离，审核结论进入审计记录；
- 发布结果形成稳定、可引用的 API 契约版本；
- 先提供版本快照、Diff 和恢复，不在本阶段建设完整 Git 式分支系统；
- 未启用审核的中小团队继续保持直接编辑体验。

#### E2 阶段验收门槛

1. 一个多人项目可以完成提交、审核、发布和恢复闭环；
2. 人工、同步任务、CI 和 Agent 变更能够在同一历史视图中区分来源；
3. 审核策略不能绕过统一权限、Secret 和审计边界；
4. 关闭审核后不增加现有直接编辑流的必要步骤。

### 阶段 D1：受治理的 Agent 与主动诊断

**目标：** 在企业基础能力上形成差异化，而不是让 Agent 成为治理旁路。

- MCP 继承 workspace/project 权限、服务账号、Token、Environment 和审计规则；
- Agent 复用 Contract Sync 引擎读取来源、生成 drift report、提出合并方案并按项目策略写入或进入审核；
- Agent 不能读取 Secret 明文，只能请求在授权执行环境中解析 Secret Reference；
- Mock、示例请求、Contract Validation 和测试结果绑定到同一契约版本；
- 提供 Proxy/Trace/Contract Guard，回答实际请求、网络、证书、Token 和契约漂移问题；
- 提供 Scenario、跨接口 E2E 和回放，运行结果关联契约版本和执行身份；
- 规则先使用内置配置，不建设复杂规则编程平台。

#### D1 阶段验收门槛

1. Agent 不能获得超过其服务账号和项目策略的权限；
2. Agent 变更可预览、可审阅、可追溯、可撤销；
3. Agent、人工同步、CI 和 Runner 使用同一 Contract Sync 与 Validation 引擎；
4. 一个已发布契约可以驱动 Mock、验证、诊断和至少一个跨接口场景。

### 阶段 P1：平台扩展

**目标：** 仅在 G0、G1 和持续工程闭环得到验证后，扩展协议、组织规模和基础设施。

候选方向包括：

- 未被目标企业提升为 G0 条件性门槛的多 IdP、复杂组织映射和自定义角色；
- 未被目标企业提升为 G0 条件性门槛的多节点 HA、跨区域灾备、SIEM 和外部 Vault/KMS；
- OpenAPI 3.1/3.2、Arazzo 和 SDK 生成；
- WebSocket、gRPC、Dubbo、MQTT、TCP 和 Serial；
- 通用 Proxy、External Handler 和私有协议 Analyzer；
- public/internal/admin 路由分层；
- YApi 业务数据迁移到 PostgreSQL 或其他存储；即使迁移也必须与 Enterprise Control 和 Casdoor 保持独立 database。

这些方向不自动进入实施。必须由真实企业需求、现有架构瓶颈或明确商业机会触发；一旦进入已承诺目标企业的采购、安全或生产清单，对该客户即重新归类为 G0 条件性门槛。

## 8. 明确非目标

以下事项不属于 G0/G1 门槛主线：

- 为了视觉一致性继续大规模重构 Web；
- 完整复制 Apifox、Postman 或 SwaggerHub 的功能矩阵；
- 补齐与企业准入无关的全部 YApi 边缘接口和历史插件；
- 同时支持所有 SSO、目录和人员同步协议；
- 在 G0 权限、审计以及 G1 同步、Schema、Environment 基础未统一前建设复杂审批编排器；
- 在真实需求出现前建设完整 Git 式 API 分支；
- 在主服务进程中恢复任意高级 Mock 脚本执行；
- 为少数客户私有逻辑建设无约束插件市场；
- 多协议、PostgreSQL、通用网关、计费或 SaaS 多租户；
- 桌面应用打包和与 G0/G1 无关的客户端形态扩展；
- 以单元测试数量、页面数量或接口数量作为产品阶段完成标准。

现有功能的严重缺陷、安全问题和数据损坏风险仍需修复，但普通体验优化和差异化功能不能挤占 G0 主线资源。

## 9. 产品度量

### 9.1 北极星结果

北极星不是功能数量，而是：

> 有多少目标企业完整通过 G0 准入门槛并进入生产；其中有多少企业继续通过 G1，把真实 API 项目持续运行在 ApiMind 中。

第一层衡量“能否采购和生产”，第二层衡量“能否替换和持续使用”。只有两层都通过，才形成完整企业采用。

### 9.2 核心指标

| 类型 | 指标 |
| --- | --- |
| G0 企业准入 | 完成准入矩阵的目标企业数、准入通过率、从评估进入生产的转化、主要否决项 |
| G0 身份与权限 | 企业身份接入成功率、人员停用生效率、越权失败数、公开分享策略覆盖率 |
| G0 审计与凭据 | 关键操作审计覆盖率、服务账号采用率、Token 撤销生效率、Secret 暴露事件数 |
| G0 运维 | 备份成功率、恢复演练成功率、升级成功率、可回滚升级比例 |
| 数据进入 | 成功迁移的真实项目数、活跃 Contract Source 数、首次导入成功率 |
| 持续同步 | 重复同步成功率、漂移解决率、冲突处理结果、人工字段保留率、幂等失败数 |
| Schema | 往返一致率、无法表达或被降级字段数、Contract Validation 通过率 |
| G1 安全执行 | 使用 Auth Profile、Secret Reference 和 Network Profile 的真实项目数，请求执行成功率与脱敏失败数 |
| 激活 | 完成部署、创建 workspace、导入真实项目并邀请第二位成员的团队数 |
| 自动化 | 服务账号使用比例、Runner 成功率、定时同步与测试成功率、机器可读报告采用率 |
| 治理 | 受 RBAC 保护的活跃项目比例、关键操作审计覆盖率、可恢复变更比例 |
| 规模 | 大项目加载、迁移和同步性能退化，长任务恢复成功率 |
| 留存 | 持续维护真实 API 的活跃团队和活跃项目 |
| 商业 | 从评估进入生产的转化、组织生产授权意愿和主要阻塞原因 |

本 Spec 不预设具体数值目标。首批企业试点用于建立基线，再为后续版本设置目标；不能为了达成指标降低权限、审计或恢复门槛。

## 10. 产品决策原则

后续需求按以下顺序判断：

1. **是否阻塞企业采购、安全评审、内网运行或生产部署；**
2. **是否影响身份、权限、凭据、审计、备份和恢复；**
3. **是否影响真实 API 数据的完整迁移、持续同步和安全执行；**
4. **是否是团队每天都会遇到的环境、鉴权、网络或 Schema 问题；**
5. **是否同时服务企业、中小团队、人工和自动化；**
6. **是否为多个后续能力提供共同基础；**
7. **是否有真实客户、采购、试点、issue 或运行证据。**

优先级规则：

- 缺失会否决企业采购、安全评审或生产部署：进入 G0；
- 缺失会导致现有工具无法可靠替换、同步或安全执行：进入 G1；
- 缺失会阻碍无人值守运行和持续工程：进入 E1；
- 缺失会阻碍团队规模化治理：进入 E2；
- 能形成差异化但依赖企业基础：进入 D1；
- 只服务未来场景或少数客户：保留在 P1 候选池。

## 11. 关键产品决策

本 Spec 作出以下默认决策，除非真实客户证据要求调整：

1. G0 企业准入门槛是全局第一目标，G0 未通过前不以 G1、自动化或差异化作为主投入；
2. G0 使用基础企业配置加条件性企业配置，不把所有高级能力一律实现，也不把已承诺客户硬门槛固定后置；
3. 服务账号、Project Token、Secret 基础和统一审计属于 G0，不随 Runner 后置；
4. 核心功能不依赖 ApiMind 官方云服务，Telemetry 和所有外部依赖可关闭或替换；
5. 不默认新增“组织”业务层级；实例与 workspace 能否覆盖目标企业治理标记为“需要验证”；
6. Contract Source & Sync 是 G1 第一主线，不把持续同步继续视为导入页面附属功能；
7. Source Binding、Compare、Merge 和 Report 由统一引擎提供，Web、MCP、CI 和 Runner 不各自实现；
8. Schema 是文档、Mock、验证、测试和 Agent 的共同基础，任何导入降级必须显式报告；
9. Environment、Auth Profile、Secret Reference 和 Network Profile 是四个独立产品模型；
10. 高频、标准、跨企业重复出现的能力由官方内置，客户私有逻辑通过受控 Adapter 或 Handler 接入；
11. Webhook 先于企业消息平台专用适配，版本快照和恢复先于完整分支模型；
12. 动态 Mock 必须隔离和限权，不能恢复任意宿主代码执行；
13. Agent、CI 和 Runner 使用 G0 服务账号，不继承个人长期凭据，也不能读取 Secret 明文；
14. Web、HTTP、MCP、同步任务和 Runner 不允许拥有不同的授权、合并、Schema 或 Environment 语义；
15. 备份、恢复、升级和回滚属于产品能力，不只作为运维文档存在；
16. 企业能力默认不增加中小团队的首次使用步骤；
17. 真实企业试点可以调整条件性配置，但不能跳过 G0 直接扩展 G1 或差异化功能。
18. 企业身份、授权、服务身份、审计和 `ecp-ui` 由 ECP 提供，ApiMind、GPTS、AG Insight、NexTerm 通过 Product Manifest 与 `ecp-connector` 接入；
19. Casdoor 直接承担 IAM 和优先采用的 Casbin 授权引擎；`ecp-api` 不得重复实现密码、MFA 和通用 IdP，也不得直接访问 Casdoor 数据库；
20. Casdoor、ECP 和产品业务数据始终使用独立 database，即使未来采用相同数据库引擎也不合库、不共享表。

## 12. 风险与验证

| 风险 | 影响 | Roadmap 约束 |
| --- | --- | --- |
| 用社区 issue 频率替代企业准入证据 | 高频功能挤占 G0，第一目标漂移 | 分离采购/试点、竞品企业版、社区反馈和差异化四类证据 |
| 条件性企业配置无限扩张 | G0 永远无法完成 | 只为已确认目标企业建立准入矩阵，未承诺需求保留在候选池 |
| 实例加 workspace 无法覆盖真实组织治理 | 企业权限模型在规模化时返工 | 在实施前用目标企业组织结构验证；不足时将组织模型提升为条件性 G0 |
| 同步静默覆盖人工内容 | 直接破坏企业信任和长期采用 | 所有同步先 Compare/Preview，定义字段所有权、冲突和失效资源策略 |
| 导入 Schema 降级但未报告 | 文档、Mock、验证和代码生成同时出错 | 建立往返一致性与字段损失报告，禁止静默降级 |
| Web、MCP、Runner 各自实现同步或环境语义 | 相同项目产生不同结果 | 统一 Source/Sync、Schema、Environment 和执行服务边界 |
| Secret 进入日志、导出或错误信息 | 造成真实凭据泄露 | 使用 Secret Reference、集中解析和默认脱敏，并加入泄露回归门禁 |
| 企业代理、证书和 OAuth 只在部分入口可用 | GUI 可用但 CI/Runner 失败 | Network/Auth Profile 由 Go 侧统一执行并跨入口验证 |
| 在现有 YApi 兼容权限上叠加新模型 | Web、HTTP 和 MCP 权限不一致 | 先建立统一授权边界，再扩展角色和身份协议 |
| 审计只覆盖新功能 | 企业无法获得完整追溯 | 定义统一事件模型，并逐步收口所有关键写路径 |
| 备份存在但无法恢复 | 形成错误安全感 | 每个支持版本必须进行恢复演练和结果校验 |
| 大项目同步和历史导致性能退化 | 产品在真实企业规模下不可用 | 使用代表性企业数据做分页、索引、异步任务和恢复测试 |
| Casdoor 与目标客户身份源或生命周期要求不匹配 | 企业试点仍被阻塞 | 在实施前验证目标客户 IdP、SCIM 和 Group Sync 要求；通过标准协议和受控 Adapter 集成，不直接依赖 Casdoor 数据库 |
| ECP 抽象不足或过度通用 | 产品重复建设或 G0 范围失控 | 只统一身份、固定角色、服务身份、审计和运维；产品业务语义通过 Manifest 与 Connector 保留在产品侧 |
| 企业能力让小团队使用复杂化 | 降低自然采用 | 企业功能按需启用，本地账号和内置角色保持最短路径 |
| 追逐竞品功能数量 | 稀释资源并延迟准入 | 只实现采购门槛、共同基础和真实客户证据支持的能力 |
| Agent 绕过人工和权限边界 | 造成高风险自动化写入 | Agent 必须使用服务账号、同一授权、审计和项目审核策略 |

进入每个实施 Spec 前必须重新核对当前代码、公开契约和真实部署状态。无法从当前代码确认的能力标记为“需要验证”，不得因为旧页面、历史文档或 Roadmap 中存在名称就视为已完成。

## 13. Roadmap 成功定义

本 Roadmap 成功不是因为 ApiMind 拥有更多菜单，而是因为：

- 企业 IT 能够部署、升级、备份和恢复；
- 企业身份能够接入，成员离开后访问权可撤销；
- 管理员能精确控制 API 资产读写；
- 安全人员能够追溯关键操作；
- CI、集成和 Agent 使用独立、受限、可撤销的机器身份；
- 目标企业的采购、安全和生产准入矩阵可以完整通过；
- 真实 YApi 和 OpenAPI 项目能够迁移并持续同步，人工内容不会被静默覆盖；
- Schema、Example、Mock 和验证使用同一可靠契约基础；
- 企业环境、鉴权、Secret、代理和证书能够安全复用；
- Runner 能够复用相同身份、权限和执行模型；
- GUI 中的核心能力可以无人值守运行并生成机器可读结果；
- 团队能够对 API 变更进行历史查看、审核、发布和恢复；
- 中小团队仍然能够以简单方式使用同一产品；
- 在这些基础上，Agent、Scenario 和多协议能力形成可持续差异化。

最终产品方向是：

> 先通过企业采购、安全和生产准入门槛，再成为可持续替换现有工具的自托管 API 基础设施，最终发展为 Agent 驱动的 API 生命周期平台。
